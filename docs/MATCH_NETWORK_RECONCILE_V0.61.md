# M3.49 网络响应丢失后的安全回读与重复出牌防护（v0.61）

## 修复动机

M3.48 已支持**同标签页刷新后**通过 sessionStorage 中的随机会话令牌恢复原人机对局，但它没有完全处理更危险的一种网络异常：浏览器发送碰、杠、胡或切牌操作以后，服务端可能已经修改了牌局，**HTTP 回复却在途中丢失**。旧页面这时显示「操作未完成」，而实际牌局可能已经进行。用户再次点同一按钮会发出重复、与服务端实际牌局冲突的请求。

## 实现

- 将原有只读 `match_resume` 接口的客户端逻辑重构为 `fetchMatchSnapshot`（仅携带会话令牌）和 `acceptMatchSnapshot`（清理旧动画、无声接收已经确认的服务器状态）。不新增会话查询端点，不允许任意指定玩家座位。
- 当**已有对局的游戏操作**遇到断网、响应解析失败或服务器5xx等结果不明确的情况，**不重新发送原出牌/碰杠胡请求**，只调用 `match_resume` 查询真实牌局。如已成功执行，采用服务端当前手牌、牌河、法定响应选项及正式积分；原来的旧动画和语音不当成新动作重播。
- 如果只读同步也失败，设置 `recoveryRequired` 锁，暂停下一次出牌、胡、碰、杠和自动 AI 连续推进，桌面明确提示「本步结果尚未确认，已暂停出牌与碰杠」，提供「重新连接原对局」按钮。恢复成功后解锁，继续以服务器需要的下一步为准。
- 服务器明确返回4xx拒绝（参数不合法等）时保留原本的错误提示和交互，不以「网络不确定」处理；已失效会话则清除本标签页会话令牌，隐藏过期牌桌。
- 新开一局的令牌若从未到达浏览器不能被猜测或恢复；用户仍可按原流程重新开始。没有新增数据库持久化实时墙牌／其他玩家手牌。

## 新增验证

- 在真实 JS 牌桌 DOM 回归中模拟「服务端已处理某次手切，浏览器收到网络异常」，验证请求顺序是 `match_discard` → **只读** `match_resume`，最终手牌张数和牌河对应服务端记录，且只发出一次 `match_discard`。
- 再模拟断网后只读恢复也失败，验证同一张手牌多次点击都不会再发送出牌，只有用户按「重新连接原对局」并从服务器获得正确状态才恢复操作。
- 保持 M3.48 刷新恢复、旧失效令牌清理、游戏规则与历史战绩图表完整 CI。

## 已知边界

恢复只保证服务端进程内会话仍然存在；服务端重启后无法还原未结束的隐蔽牌墙。若本地浏览器停用 `sessionStorage`，仍可在当前页面内游戏，但刷新后无法自动找回令牌。本轮不伪造这种持久恢复。没有使用远端服务或者传出用户牌局数据。
